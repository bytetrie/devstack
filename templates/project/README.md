Common commands (inside the container):

```sh
sudo devstack-sync restart app            # after editing server.ts
journalctl -u @@SERVICE@@ -f              # app logs (no sudo needed)
./infra/compress-static.sh static error   # after editing static files (if precompression is on)
sudo devstack-sync validate caddy         # check infra/Caddyfile without applying it
sudo devstack-sync reload caddy           # after editing infra/Caddyfile
scripts/sync-env.sh                       # after adding a line to infra/apt-packages.txt
pnpm lint:changed                         # lint what changed since the last commit (before committing)
pnpm check                                # type check + lint everything (what CI should run)
sudo devstack-sync status                 # services, egress profiles, last package sync
curl -s https://@@DEV_HOST@@/api/health   # the app through Caddy (the container trusts the dev CA)
```

Call the app through Caddy (`https://@@DEV_HOST@@`), not on port @@APP_PORT@@: without
Caddy's internal token the app answers every request with a bare 500. In a browser, only the
site's own pages may call it: Caddy answers requests from other sites with 403
(`caddy.same_origin`; `curl` and other tools pass). Open the site from the host with
`devstack browse`, a Chromium that reaches only the dev domain. A dev server listed in
`caddy.dev_servers` (e.g. Vite on 5173) is served at `https://<name>.@@DEV_HOST@@/` with
`/api/*` going to the app: `devstack browse <name>`. Node trusts the
dev CA through `NODE_EXTRA_CA_CERTS`, which login shells get from
`/etc/profile.d/devstack-ca.sh`; set it yourself for processes started another way.

## What runs where, and with which rights

- **You, VSCode, extensions, terminals and coding agents** all run as `@@USER@@`.
  It has no general root: `sudo` only runs `devstack-sync` (the commands above).
  Root for you is `incus exec @@STACK@@ -- bash` from the host. It has full internet
  access, but the host and your LAN are blocked by an incus network ACL on the host.
- **To add a system package**, add a line to `infra/apt-packages.txt` and run
  `scripts/sync-env.sh`. Never `apt-get install` by hand: it isn't allowed, and a
  hand-installed package is gone on the next rebuild. Services that a package ships
  are masked; a service the app depends on is a devstack change on the host.
- **The app** (`@@SERVICE@@`) runs as `@@APP_USER@@`. What it may reach going out is its
  egress profile (`app.profile`, default `local`: loopback only, no DNS), enforced by
  nftables. Its only writable folder is `$STATE_DIRECTORY` (`/var/lib/@@APP_USER@@`, a
  persistent volume). You can read that folder but not write it: writes go through
  the app. Back it up with `devstack data backup` on the host.
- **Runners** (`[[app.runners]]` in the devstack config) are for tools that need the
  internet or parse untrusted files. Each connection to a runner's loopback port starts
  one job as `@@RUNNER_USER@@`: public internet, no loopback, no secrets, and its only
  writable folder is `$INCOMING_DIR` (`/var/lib/@@APP_USER@@/incoming`). Treat everything
  that lands there as untrusted input. Note that an app that may send a runner any URL
  can reach the internet through it. `AGENTS.md` has the whole contract; writing a runner
  without reading it wastes a round trip.
- **Tests**: the integration test database is `TEST_DATABASE_URL` in
  `~/.config/devstack/@@STACK@@.env` (with `DATABASE_URL` for dev tools; e.g.
  `node --env-file-if-exists=$HOME/.config/devstack/@@STACK@@.env`). Make test setup
  refuse to run unless the database name ends in `_test`.
- **Git**: all of `.git` is read-only in the container (the host runs git on it), so
  commit, branch and push on the host; in the container git can only read. Don't
  create a repository inside the project: the host's git would run its config.

`infra/devstack-requires.toml` is what this project needs from its container: image,
Node, Postgres, app and Caddy settings, whether it needs the GPU, and the host folders it expects mounted (by name
and container path only). It holds nothing about any host, so it stays in git. Your own
devstack config (host paths, ssh, DNS, and where each mount comes from) stays outside
the repo. To build the environment on another machine: clone this repo, run
`devstack init --project <this folder>` (it takes the requirements as defaults and asks
for each mount's host folder), read the config it wrote, run `devstack up -c <it>`,
then `devstack db restore <dump>`.

## Trust boundary

The container is where untrusted code (npm packages) runs, but two channels reach the
host by design: ssh / VSCode Remote-SSH into the container, and this project folder,
which is shared **read-write** with the host. Treat anything in this folder as untrusted
when you run it on the host (`.vscode/`, `package.json` scripts, shell scripts).
All of `.git` is mounted read-only inside the container; add other paths the host runs
from there to `project.readonly_paths`. Review what you push as commits
(`git log -p @{u}..HEAD`), not only as a working-tree diff.

Inside the container, the app and runners can't do more than their profiles allow,
even if their code is edited. The container user (and so every agent) can still use
the real database as the app role, read the app data and use the internet: that is a
deliberate trade-off for development, not something the isolation prevents.

## Dependencies

The **inventory** is generated, not written by hand: `@@SBOM_DIR@@/container.cdx.json`
(everything installed in the container: Debian packages, Node, Caddy, Postgres) and
`@@SBOM_DIR@@/app.cdx.json` (this project's npm packages, from `pnpm-lock.yaml`).
Both are [CycloneDX](https://cyclonedx.org/), produced by
[syft](https://github.com/anchore/syft) inside the container, and both are committed.

```sh
./devstack sbom show            # what is in them (on the host)
./devstack sbom generate        # refresh them after changing a dependency
./devstack sbom check           # fails if they no longer match the container
./devstack sbom scan            # grype: known vulnerabilities in what is committed
```

`devstack up` refreshes them for you. They are normalized so the bytes depend only on
the dependency set: no timestamps, no run-to-run ids, so a diff means a real change.
Do not hand-edit them — `sbom check` is the gate, and a manual edit just fails it.

What this file is for is the part a generated inventory cannot hold — **why**:

- The app starts with **zero runtime npm dependencies**: `server.ts` uses only `node:`
  built-ins. Adding a runtime package is a decision; note it and the reason here.
- npm packages come in through pnpm with a committed `pnpm-lock.yaml`. Never
  `npm install` into this project. A new dependency, and any change to the lockfile, is
  reviewed by a person; agents must say when they add one.
- The dev toolchain is TypeScript (held at 6.0: typescript-eslint, which the type-aware
  lint needs, does not support 7 yet), `@types/node` for the container's Node major, and
  ESLint with typescript-eslint (`strict-type-checked`), `eslint-plugin-security`,
  `eslint-plugin-no-unsanitized` and `@eslint-community/eslint-plugin-eslint-comments`.
  There is no separate static-analysis tool (Semgrep, Opengrep), so `eslint.config.js`
  carries those checks. A rule turned off needs the reason beside it.
- `pnpm-workspace.yaml` limits what pnpm installs: nothing published less than 7 days
  ago (`minimumReleaseAge`), transitive dependencies only from the registry
  (`blockExoticSubdeps`), no version whose publishing trust dropped (`trustPolicy`), and
  no dependency install scripts unless `allowBuilds` lists the package (`strictDepBuilds`).
  An `allowBuilds` entry or an exception is a decision: record it and why, here.
- pnpm itself is pinned, with its hash, in `package.json`'s `packageManager`.
- System packages go in `infra/apt-packages.txt` (Debian names only) and are installed
  by `scripts/sync-env.sh` through `sudo devstack-sync packages`. Never `apt-get
  install` by hand: it is not allowed, and a hand-installed package is gone on the next
  rebuild.
- Third-party apt repos and downloads are only used with a pinned signing key or a
  pinned sha256, checked before use, so a swapped download fails the build instead of
  being trusted. Those pins live in devstack, not here.
- An entry in `sbom.ignore` (a vulnerability the scan should stop counting) is a
  decision too: record the id and why, here.

Checks run in the container (`pnpm lint:changed` before committing, `pnpm check` for
everything), not in git hooks: `.git` is read-only in the container, and a hook would be
project code the host's git runs. `lint:changed` only reads `.git`, which works read-only,
but needs the `git` program in the container: add `git` to `infra/apt-packages.txt`, or
it lints everything instead. In CI, whichever you use, make this a blocking step:

```sh
corepack enable                   # pnpm at the version and hash in packageManager
pnpm install --frozen-lockfile    # exactly the lockfile, re-checked against pnpm-workspace.yaml
pnpm check                        # tsc --noEmit, then eslint --max-warnings 0
```

A CI config in the repo is a file the container can edit; add its folder to
`project.readonly_paths` if agents shouldn't.

Deliberately not used, so they are not added without a reason:

- **Runtime frameworks and DB drivers** in the starting app: it is a zero-dependency
  smoke test.
- **Debian's `nodejs` package / NodeSource**: an exact, signature-verified Node release
  is pinned instead.
- **Docker**: an incus system container gives a full systemd userland that mirrors
  production (Caddy, the app unit and Postgres as services).
- **A build step for TypeScript**: Node runs the sources directly.
