devstack · run/setup

devstack field guide

One command builds a generic environment for a full-stack web app: an incus container on your machine that you develop in, that runs the app the way production will, and that keeps your database between rebuilds.

What it builds

The result is two things at once:

  • A local dev environment. VSCode connects over ssh into the container. The project folder lives on your host and is shared into the container, so your editor, git and backups all see the same files.
  • A local containerized app environment. Caddy serves the app at its real domain with a dev suffix and local TLS. The API runs as a hardened systemd service, and Postgres listens on loopback only. This is close to how the app will run when deployed.

The whole build is described by one devstack.toml, which stays on your machine. The project carries only what it needs from the container, in infra/devstack-requires.toml, so you can rebuild the same environment on another machine, or start a completely new project from the same setup.

Host

  • Browser → https://app.example.com.devbox
  • VSCode Remote-SSH → devbox
  • dnsmasq: address=/devbox/<ip>
  • devstack's root CA (key stays here, limited to the dev domain) in the trust store
  • ~/code/devbox (your files)

Kept outside the container

  • incus volumes devbox-pgdata, devbox-appdata
  • incus network ACL devstack-devbox: container ↛ host, LAN
  • db dumps and app data archives in ~/.local/share/devstack/…
  • journal + state in ~/.local/state/devstack/…
incusbr0 bridge · pinned IPv4

Container devbox (debian/13)

  • sshd, key-only, one user with your uid; its only root command is sudo devstack-sync
  • ufw: in 22, 80, 443 only · nftables: per-service egress profiles
  • Caddy :443 → static files from /srv/devbox/static, /api/* → 127.0.0.1:8080 with an internal token; admin API on a root/caddy-only socket
  • devbox-app.service: Node as devbox-app, read-only except /var/lib/devbox-app (volume), egress: loopback only
  • runners (optional): one job per connection as devbox-runner, egress: public internet only
  • services (optional): a pinned download per service (e.g. Ollama), each as its own user, egress: loopback only by default; with gpu = true, the only thing that can use the GPU
  • Postgres 18 on 127.0.0.1:5432, data on the volume at /var/lib/postgresql
  • /srv/devbox = your project folder (idmapped mount)

Names above are the defaults for stack.name = "devbox". Change that one key and every name follows.

Why it's built in layers

Each phase adds one concern on top of the last, so you can stop after any of them and see what that layer gives you:

contain
Dev work (npm packages, build tools, the app) runs in a container, so user-level but possibly untrusted code can't reach your host's files or processes. Your editor stays on the host and connects in over ssh.
serve
A tiny zero-dependency server proves the container can run an app that reads files and answers requests. It's a smoke test, not your app.
proxy
Caddy sits in front of the app. You browse to the real intended domain plus a dev suffix (app.example.com.devbox for a future app.example.com), over HTTPS, with no port numbers. Caddy serves static files itself and forwards /api/* to the app.
standards
Client-side safety and speed: precompressed files, response compression, and security headers including a Content Security Policy.
isolation
Server-side safety: the app listens on 127.0.0.1 only (never 0.0.0.0, the top rule), a firewall backs that up, the app only answers requests carrying a secret token that Caddy adds, and it runs as a tightly restricted systemd service under its own user, whose outbound traffic the kernel limits (loopback only by default). Tools that need the internet run as separate, short-lived runners. You (and every agent) get no general root, so nothing you can edit runs as root.
data
Postgres, local-only with password auth, with its data kept outside the container so it survives rebuilds.

Host DNS

devstack assumes the host already resolves through dnsmasq, set up once by hand (see below, including any VPN workaround). It never touches /etc/resolv.conf, NetworkManager or /etc/hosts. For each stack it writes exactly one file and restarts dnsmasq:

# /etc/dnsmasq.d/devstack-devbox.conf
address=/devbox/10.60.225.x       # the TLD and every name under it
host-record=api.other.test,10.60.225.x   # one per dns.extra_names

Adding a stack adds one file, and removing a stack removes it. With dns.tld = "" you get the single-domain case: site.hostname itself points at the container, useful for overriding a real domain locally. devstack warns about it, because that name then stops resolving to the real site for the whole machine.

dns.tld must not be a real top-level domain (com, dev, app, ...): address=/dev/<ip> would send every .dev site to the container. devstack checks the value against a bundled IANA list and refuses; dns.allow_public_tld = true overrides that. Good choices are the default (your stack name), internal (reserved for private use) or any unused name. Since a stack name becomes the default TLD, a stack called app or dev is refused too unless you set another dns.tld.

One-time setup

devstack doesn't do this for you, because it changes how your whole machine resolves names. In outline:

  1. sudo apt install dnsmasq, and note the DNS servers currently listed in /etc/resolv.conf.
  2. Add a base file in /etc/dnsmasq.d/ with no-resolv, one server=<upstream> line per old DNS server, listen-address=127.0.0.1 and bind-interfaces. If the old file had a search domain, add matching domain= and local= lines. Restart dnsmasq.
  3. Back up /etc/resolv.conf, then set it to nameserver 127.0.0.1.
  4. Stop NetworkManager rewriting it: add dns=none under [main] in /etc/NetworkManager/NetworkManager.conf.
  5. A VPN client that manages DNS itself may still overwrite the file. One workaround is a second dnsmasq listen address on lo (a oneshot systemd unit that runs ip addr add <addr>/32 dev lo before dnsmasq starts), then point the VPN's custom DNS setting at it.
  6. Reconnect the network or VPN and reboot once, and check that /etc/resolv.conf still says 127.0.0.1.

To confirm the host really uses dnsmasq before you start, add a throwaway address=/dnscheck/127.0.0.2, restart dnsmasq, and run getent hosts x.dnscheck. It should print 127.0.0.2. Remove the line afterwards.

Editor backups are loaded too

Debian's dnsmasq loads every file in /etc/dnsmasq.d/ except .dpkg-* ones, so an editor backup like mystack.conf~ is active as well. It's harmless while it matches the original, but it will shadow later edits. Preflight warns about such files.

If you already have a hand-made container or dnsmasq setup, pick a stack.name that doesn't reuse its names. Preflight stops if a configured name is already taken by something devstack didn't create.

First run

Do it in stages the first time, so each layer is easy to inspect.

cd path/to/devstack
./devstack init                 # walk through every setting, writes devstack.toml
./devstack preflight            # checks only, changes nothing
./devstack plan                 # every step with the real names and paths
./devstack up --to base         # container, user, ssh, Node
ssh devbox                    # look around
./devstack up                   # the remaining phases
./devstack status

Then run ./devstack browse: it opens https://app.example.com.devbox/ in a Chromium that can reach only the dev domain (see The dev browser). In VSCode, choose Remote-SSH → devbox → open /srv/devbox.

Configuration

devstack.example.toml lists every key with its explanation and default. Every key is optional. In short:

  • Values can refer to other keys: "~/code/{stack.name}". Computed values are {env.user}, {env.uid}, {env.home} and {stack.name_sql} (the name with - turned into _).
  • Unknown keys are errors, so a typo never silently falls back to a default.
  • ./devstack config explain [KEY] prints the docs, config show the resolved values, and config check validates the file.

Your config holds details about your host, so it is never copied into the project. Instead, up writes <project>/infra/devstack-requires.toml with just the container-side settings (image, Node, Postgres, app, Caddy, firewall, GPU) and the host folders the project expects, listed by name and container path only. Commit it. Anyone setting up the project runs ./devstack init --project <folder>, which takes those settings as defaults and asks where each folder lives on their host. devstack only accepts container-side settings from that file, so a repo can't use it to change anything on your host. If it differs from your config and you didn't write it (it came with a clone or a pull), up asks before overwriting it.

Read a devstack.toml before you run it

A config decides which host folders are mounted into the container, which incus profiles and image are used, and which host files are written. Treat one from somewhere else like a script. ./devstack plan lists the image, profiles, shared folders and every host path that would change. Mounts of /, your home folder, ~/.ssh, ~/.gnupg, /etc, /root or /var need you to type yes (or pass --yes in non-interactive mode), and so do settings that widen access: container.sudo = "full", app.profile = "open", network.allow_private exceptions, and every new or changed runner. Profiles other than default and images from outside images: produce a warning.

Undo and rollback

Nothing is left half-done that you can't get out of. Two mechanisms cover everything devstack changes:

inside the container
A snapshot is taken before each phase (after base). Undoing a phase restores it, which reverts packages, config files, services and device config in one go.
everything else
A journal (~/.local/state/devstack/<name>/journal.jsonl) records every host and project change before it is made. Undo replays it backwards. Replaced files are restored from backups, and created files are removed.
./devstack undo                  # undo the last phase
./devstack undo --to proxy       # undo everything after proxy
./devstack destroy               # undo all; the Postgres volume is kept
./devstack destroy --purge-data  # …and delete the volume (a pg_dump is taken first)

When a phase fails, devstack offers to roll back just that phase. Earlier phases stay as they are. Every undo step is safe to repeat, so if an undo is interrupted, run it again.

ActionContainerProject filesPostgres volumeDumps

Your edits are safe

Before undo removes a project file, devstack compares it with a hash of what it wrote. Anything you changed is kept, with a warning. The same goes for infra/Caddyfile and the unit copy.

Don't delete the state folder

~/.local/state/devstack/<name>/ is how devstack knows what it owns. Without it, undo can't help, and the next run treats your own container and volume as conflicts. If that happens, see Troubleshooting.

Snapshots

On the dir storage driver, each snapshot is a full copy of the container (a few hundred MB). Snapshots are kept until you remove them, because they are what makes per-phase undo possible.

./devstack snapshot list            # shows which phase each snapshot can undo
./devstack snapshot prune           # delete phase snapshots of finished phases
./devstack snapshot create before-x # a bare container snapshot, outside devstack's bookkeeping
incus snapshot restore devbox before-x
  • snapshots.cleanup = "manual" (default) keeps them until you prune. "auto" prunes after up finishes with everything verified.
  • After pruning, those phases can only be undone with destroy. Your data volume is still kept.
  • Restoring a manual snapshot with incus snapshot restore goes around devstack. Its phase list may then not match the container. Run ./devstack up --redo <phase> for anything that looks off.
  • Snapshots never include the Postgres volume, so rolling the container back never rolls back your data. To roll back everything together, use a checkpoint.

Checkpoints: undo everything since

Phase snapshots undo provisioning. A checkpoint undoes what came after: an agent that went off the rails, a bad install, test data you don't want. It captures the container, its data volumes and the project together, and one command puts all three back.

./devstack checkpoint create [NAME]   # default name: the date and time
./devstack checkpoint list
./devstack checkpoint restore NAME
./devstack checkpoint delete NAME
PartHow
the container (packages, system files)an incus snapshot, checkpoint-<name>
Postgres, app data in volume modeincus volume snapshots; app data in host mode is archived through the container
tracked and untracked project filesa commit on refs/devstack/checkpoints/<name>, made without touching your branches, HEAD or staged changes, and without running hooks, filters or anything from your git config
small ignored files (.env, local scratch data)copied, up to checkpoint.capture_max_mb in all; anything over is listed as not captured
derived folders (node_modules, dist; checkpoint.derived)not copied: checkpoint.restore_command (default pnpm install --frozen-lockfile) rebuilds them after a restore
  • The container stops while a checkpoint is taken or restored, so all parts are from one moment. Your ssh and VSCode sessions drop and reconnect.
  • Space. checkpoint.keep = 1 by default: create lists what exists, makes the new checkpoint first, then deletes the oldest beyond keep after you say yes. It measures what each checkpoint took from the storage pool, refuses to start when the pool has too little room for another, and warns about the space the kept ones use. On the dir driver every checkpoint is a full copy of the container and the data volumes.
  • Restore puts the files back as they were, removes files made since, restores the staged changes if you are on the same commit, then runs checkpoint.restore_command. Commits made since are kept; if HEAD moved, it shows how to look at them and how to drop them (git reset <then>). It never writes through a symlink the container may have put in the project.
  • Only with the same phases done. A checkpoint taken before an undo or up --redo can't be restored after it: the container would no longer match devstack's records.
  • Recovery, not containment. A checkpoint taken after something malicious ran restores it too, and one taken before can't undo anything that already left the container.
  • destroy leaves checkpoints' leftovers (volume snapshots, the git ref); checkpoint list marks them incomplete and checkpoint delete removes them. The ref holds untracked files' contents; plain git push never sends it (only --mirror would).

Keeping your data

Postgres data lives on its own incus volume, not in the container. As you build features, you can rebuild, undo or destroy the container without losing rows. Running up again re-attaches the volume and reuses the data:

  • The postgres OS user has a fixed uid (postgres.system_uid, 500), so the files keep the right owner in a new container.
  • The cluster config is mirrored onto the volume and restored on rebuild.
  • The app password is regenerated on a fresh container and set on the existing role.
  • A major-version change (e.g. 18 → 19) stops with an error. Upgrades are done by hand with a dump and restore.
./devstack db backup               # pg_dump -Fc into postgres.backup_dir
./devstack db restore FILE.dump    # takes a safety backup first; runs as the app role, not superuser
./devstack db shell                # psql as the app role

The app gets DATABASE_URL and PG* variables from /etc/app-secrets/postgres.env (root-only, passed in by systemd). Inside the container, plain psql -h 127.0.0.1 -U devbox_app devbox works thanks to ~/.pgpass, and dev tools read ~/.config/devstack/devbox.env. Integration tests use TEST_DATABASE_URL (devbox_test, empty, not backed up); make them refuse to run unless the database name ends in _test.

App data

The app's only writable folder is /var/lib/devbox-app ($STATE_DIRECTORY in the app). By default it's the incus volume devbox-appdata, kept like the Postgres volume (app.data = "host" uses a host folder instead, "none" turns it off). You can read it from your shell but not write it: writes go through the app, which keeps its own rules (for example rows ↔ files).

./devstack data backup             # tar.gz into app.data_backup_dir (also automatic before destroy)
./devstack data restore FILE       # stops the app, takes a safety backup, replaces the data

Rebuild elsewhere

  1. Commit the project, including infra/devstack-requires.toml.
  2. Take a dump: ./devstack db backup.
  3. On the new machine, set up dnsmasq as the resolver (one-time), clone the project and this folder, run ./devstack init --project path/to/project, read the config it wrote (see the warning under Configuration), then run ./devstack up.
  4. ./devstack db restore the.dump.

To start a new project from the same setup, run ./devstack init with a new stack.name. It gets its own container, TLD, volume and state, alongside the old one.

Add a host folder later

Add an entry to devstack.toml and run ./devstack up on the host. The plan lists it under mounts, and it is added to the running container without a rebuild:

[[container.mounts]]
name = "store"                 # incus device name; not project, git, pgdata, appdata, gpu, ro<N> or ro-<hex>
source = "~/code/store"        # host folder; must exist
path = "/srv/store"            # where it appears in the container
readonly = false               # default; true makes it read-only inside
  • Files keep your uid (shift = true, the default), so you can edit them from both sides.
  • It counts as part of base: undoing base (or destroy) removes it. Undoing a later phase restores a snapshot taken before the mount was added, which drops it; the next up adds it back.
  • Changing or removing an entry is not applied to the existing mount. Preflight warns when they differ; remove the device with incus config device remove <name> <device>, then run up.
  • Writable means writable for you (shells, ssh, builds). The app service still sees it read-only, like everything outside its own data folder (see Keeping your data).

Add a runner

For tools that fetch from the internet or parse untrusted files (yt-dlp, ffmpeg, page fetchers), add a runner to devstack.toml and run ./devstack up --redo isolation. A project can ask for one in its infra/devstack-requires.toml; either way you approve it with yes, because it is project code running as a service with internet access.

[[app.runners]]
name = "fetch"                       # → devbox-fetch.socket + devbox-fetch@.service
command = "node scripts/runner.ts"   # project-relative, plain words only
port = 9101                          # 127.0.0.1 only
memory_max = "2G"                    # default 1G
runtime_max = "2h"                   # default 1h
max_connections = 2                  # default 4

Each connection starts one job as devbox-runner, with the connection as its stdin and stdout; closing it ends the job. A job reaches the public internet but not loopback, your host or the LAN, gets no secrets, can't read the app data, and can only write /var/lib/devbox-app/incoming/. The protocol and what the app does with incoming/ are up to the project: treat it as untrusted input.

Add a service

For a long-running tool that isn't a Debian package, such as a local model server, add a service to devstack.toml and run ./devstack up --redo isolation. You pin the download yourself: take the sha256 from the release's checksum file, on the host. A project can ask for a service in its infra/devstack-requires.toml; either way a new or changed one needs your yes.

[[container.services]]
name = "ollama"                      # → devbox-ollama.service, user devbox-ollama
url = "https://github.com/ollama/ollama/releases/download/v0.40.4/ollama-linux-amd64.tar.zst"
sha256 = "15f31e95…"                 # all 64 hex digits; a mismatch fails the phase
command = "bin/ollama serve"         # first word: a path inside the download
port = 11434                         # optional; checked to listen on loopback only
gpu = true                           # needs gpu.enabled
env = { OLLAMA_HOST = "127.0.0.1:11434", OLLAMA_MODELS = "/models", OLLAMA_NOPRUNE = "1", OLLAMA_NO_CLOUD = "1" }
# profile = "local"                  # default: loopback only; "internet" for public internet too
# write_paths = ["/models"]          # only inside a writable [[container.mounts]] path
# memory_max = "24G"
  • Where it runs. The download is unpacked (as nobody) into /opt/devstack/services/ollama, owned by root, so neither you nor an agent can change the program the service runs. Its own state folder ($HOME) is /var/lib/devbox-ollama; a rebuild resets it.
  • What it can reach. Everything is read-only except its state folder and write_paths; the project and /home are invisible; it is in no group that reads the app data or the token. Going out, local means loopback only, no DNS, enforced by nftables on its uid.
  • Using it. You and the app reach it on its loopback port, like any local service (the app's local profile allows loopback). Its API is whatever the tool offers, usually without authentication, so anything in the container can call it.
  • Models from the host. Mount the host folder with [[container.mounts]], read-only if the service only reads it. A read-only model folder means the service can't pull or delete models: pull them on the host. With Ollama, set OLLAMA_NOPRUNE so it doesn't try to clean up at start, and OLLAMA_NO_CLOUD so it doesn't keep calling ollama.com (a local service can't reach it anyway). Ollama 0.40 and later also need a manifests-v2 folder in the model folder: it creates one on every lookup, which fails on a read-only mount unless it already exists. Create it once on the host, owned like the rest of the folder.
  • Removing an entry and running up --redo isolation stops the service and deletes its unit and download.

The GPU

With gpu.enabled, the host's GPU is passed into the container, and its driver runs in your host's kernel. By default (gpu.login_user = false) only services with gpu = true can use it: at boot, devstack-gpu.service moves the GPU device nodes out of sight of everything in the container, dev and root included, and each GPU service gets them back in its own namespace. Code you or an agent runs, and the app, can't open the GPU (nvidia-smi reports "Insufficient Permissions"). Set gpu.login_user = true to give the whole container the GPU, as before; preflight warns about it.

The dev browser

./devstack browse opens the dev site in a Chromium window that can reach only the dev domain. The container's pages are untrusted code; in your everyday browser their scripts run on your host's network, where they could reach services on 127.0.0.1 and devices on your LAN. The incus ACL keeps the container itself off both, but it can't see what a browser on your host does.

  • Only the dev domain. Everything else goes to a proxy at 127.0.0.1:9 that isn't there, so it fails rather than going direct; loopback is taken out of Chromium's usual proxy exemption, and WebRTC can't use other UDP. Checked: the dev site loads; the public internet, your host's 127.0.0.1 services and the LAN don't. browse refuses to start if something listens on port 9.
  • Its own trust. It runs with its own home folder under ~/.local/state/devstack/<name>/browser, so the dev CA goes into its own certificate store (Chromium ignores the system one). Your everyday browser doesn't trust dev sites.
  • Little else. A normal window with its own profile: no extensions, no sync, no background requests, passwords not in your keyring. --app gives an app window without tabs or address bar, still confined, but it relies on your window manager for its title bar: with a borderless or tiling setup it has none, so you can't move or close it.
  • Targets. ./devstack browse opens the app; ./devstack browse vite a dev server; ./devstack browse https://other.<tld>/ any URL under the dev domain. Anything else is refused.
  • Dev servers. List each in caddy.dev_servers (vite = "5173"; it listens on localhost in the container). Caddy serves it at https://vite.<dev host>/, with /api/* going to the app, so page and API share one origin and the same-origin rule needs no exception. No security headers there (HMR would break the CSP). If Vite's hot reload doesn't connect, set server.hmr.clientPort = 443.
  • Limits. Chromium enforces the confinement itself: a browser exploit that takes over its network process could get past it. Running it as a separate OS user with an nftables rule is stronger and not done. Reset it with rm -rf ~/.local/state/devstack/<name>/browser.

What your project depends on

Every project devstack scaffolds carries a machine-readable list of everything it depends on, in the CycloneDX format that security tools read. Two files, both committed with your code:

FileWhat it covers
infra/sbom/container.cdx.jsoneverything installed in the container: Debian packages, Node, Caddy, Postgres
infra/sbom/app.cdx.jsonyour npm packages, from pnpm-lock.yaml

They are generated by syft inside the container, because that is where the real package database and node_modules are. devstack up refreshes them for you.

./devstack sbom show      # what is in them
./devstack sbom generate  # refresh after changing a dependency
./devstack sbom check      # fails if they no longer match the container
./devstack sbom scan       # known vulnerabilities in what is committed

sbom scan runs grype on your host, not in the container. The first run downloads a vulnerability database of about 1 GB into ~/.local/state/devstack/<stack>/grype; that download is the only thing here that reaches the internet from your machine. Keeping it on the host means the container never needs it, and the reports it writes stay on the host too — a scan is true only on the day you ran it, so it is never committed.

The committed files are normalized: no timestamps and no ids that change between runs, so a diff in them always means a dependency really changed. Don't edit them by hand — sbom check regenerates and compares, so a manual edit just shows up as a failure. Your project's README.md is the place for the part a generated file cannot hold: why a dependency is there, and what you decided not to use.

Most of what a scan reports on Debian has no fix available: the counts are printed as 11 critical (0 fixable) so you can see at a glance how much of it you could actually act on. sbom.fail_on only counts the fixable ones, because failing on something no upgrade can change is noise. Set sbom.only_fixed = false if you want the stricter view.

When a scan reports something that is fixable, it tells you the command. For Debian packages, from the host: ./devstack upgrade --dry-run to see what would change, then ./devstack upgrade, which snapshots the container first, restarts only services that were already running, and refuses to replace devstack's own config. Rebuilding (destroy then up) is the other option and often the better one for a dev container: you get a current base image, and your data volumes are kept. For npm packages it is pnpm update in the container, then ./devstack sbom generate; a rebuild deliberately leaves them alone, which is what the lockfile is for.

If a scan reports something you have decided to accept, add its id to sbom.ignore in your devstack config and write down why in the project README. Set sbom.fail_on (for example high) to make sbom scan exit non-zero at or above that severity, which is what you would use in CI.

Secrets in git

You and your agents write into a folder that gets committed, and only .gitignore keeps a .env or a key file out of git. Before you push, check what actually went in:

./devstack leaks scan                # every commit, plus the current and staged files
./devstack leaks scan --no-history   # only what is about to be committed

It runs gitleaks on your host; the container doesn't need to be running. The first run downloads the pinned gitleaks binary into ~/.local/state/devstack/<stack>/gitleaks. It scans the git history, then a copy of every file that is tracked or not ignored, plus the staged version of anything staged. Ignored files such as .env are left out, as git leaves them out. Each finding shows the rule, the file and line, the commit if there is one, and a fingerprint. The secret itself is never printed, and the reports kept on the host are redacted.

The container can write anything in the project, including the files gitleaks normally reads to decide what to skip. So devstack uses its own settings only: a .gitleaks.toml, .gitleaksignore or .gitattributes in the project, or a gitleaks:allow comment in the code, has no effect on the scan.

If it finds something real, rotate the credential first. Once it has been committed, and above all once it has been pushed, treat it as leaked: rewriting history does not take it back. Then move it out of the file into an ignored .env or the container's secrets folder. If it is a false positive, add its fingerprint to leaks.ignore in your devstack config. The scan exits 5 when it finds something, so a script can stop a push on it.

Security and trust

devstack keeps untrusted code (npm packages, extensions, coding agents, anything you run while developing) inside the container. Inside it, you keep the internet and the database, but the operating system enforces the rest: nothing you can edit runs as root, services you edit stay inside their limits, and the container can't reach your host or your LAN.

Trust zones

ZoneWhoWhat protects everything else
Host + LANyouAn incus network ACL on the container's NIC, enforced by the host: the container can't open connections to your host (except DNS and DHCP on the bridge) or to private ranges. Root in the container can't change it. Exceptions: network.allow_private.
Container, as devyou, VSCode server, extensions, terminals, coding agentsNo general root: sudo only runs devstack-sync (container.sudo = "limited"). The container is disposable.
Servicesthe app, runner jobs, container.servicesA fixed system user each, an nftables egress profile matched on that user, and systemd hardening. Only GPU services can open a passed-through GPU.

You and your agents are the same Linux user (dev, carrying your uid so files in the shared folder come out owned by you on the host), so the container can't tell you apart. The rule is therefore about what runs as root, not who asks: code that runs as root is never code your user can edit, and security-relevant changes come from the host, through devstack up. When you need root, use incus exec devbox -- bash on the host.

What you and your agents can and can't do

  • Can: edit and run any project code, use the internet, use the database as the app role, read service logs and the app data, run sudo devstack-sync (install packages listed in infra/apt-packages.txt, restart the app, runners or services, reload Caddy, status), call a service on its loopback port, and change a project-owned Caddyfile.
  • Can't: become root, write the app data directly, change firewall rules or units, reach the host or the LAN, give a service more network access, use Caddy's admin API, change the program a service runs, or open the GPU (unless gpu.login_user = true). A service edited by an agent still runs under its profile: an edited app has no direct internet, and an edited runner has no secrets and can't read the app data.
  • Limits to know about: your user can send the real database and the app data out (it has both, and the internet); that's the trade-off for developing against them. An app that may send a runner any URL reaches the internet through it. Through a project-owned Caddyfile, Caddy can be made to serve anything the caddy user can read, including the intermediate CA key, which only works for the dev domain. Packages installed through devstack-sync run their install scripts as root (signed Debian packages only, and their services are masked).

An agent's own permission settings (for example, denying sudo except sudo devstack-sync) catch mistakes early, but they are not a boundary; the OS rules above are.

What reaches the host, by design

  • The browser: dnsmasq points the dev domain at the container, and the host trusts one root CA to make the padlock work. That root's private key stays on the host and is name-constrained to the dev domain (*.<dns.tld>), so even a stolen copy of the container's intermediate key can only mint certificates for dev names. Chromium and OpenSSL refuse it for any other site. Browsers that ignore name constraints are not covered, so check yours before relying on it. The container's pages run scripts, so open them in the dev browser: in your everyday browser they could reach services on your host's loopback and devices on your LAN, which the incus ACL can't stop. By default only the dev browser trusts the root (tls.browser_trust = "no"), so your everyday browser shows a certificate error on dev sites.
  • ssh / VSCode Remote-SSH into the container: key-only, one key per stack, the host key pinned from incus (no trust-on-first-use), X11 and agent forwarding off.
  • The shared project folder is read-write on the host. Code in the container can edit files you later run on the host: .vscode/, package.json scripts, shell scripts. Treat them as untrusted when you run them on the host. devstack requires git, and all of .git is read-only inside the container, because the host's git runs what it names (hooks, core.fsmonitor, core.sshCommand) and shows what its refs say. So commit, branch and push on the host; in the container git can only read. base runs git init on the host before the container exists if the project isn't a repository yet, so this holds from the start, and sets core.useReplaceRefs = false so replace refs can't change what git log shows you. A git repository nested in the project is not covered: the container can write its .git, and your git runs its config when it works in that folder (you cd there, or an editor scans subfolders for repositories). Preflight warns about each one; delete them. Add other paths the host runs from to project.readonly_paths, e.g. .vscode. On the host, don't open the folder with tools that run workspace code: an editor without workspace trust (keep VSCode's Restricted Mode for it), direnv, npm/pnpm scripts, or shell prompt plugins that switch Node versions from .nvmrc. Review what you push as commits (git log -p @{u}..HEAD), not only as a working-tree diff.
  • incus-admin group membership is root-equivalent on the host. That is how incus works; devstack needs it.

Requests from other sites

Your browser sends cookies along with requests that other sites' pages make to the app: a form posted from elsewhere, an image tag, a fetch. devstack keeps those out by default. Every site block imports a snippet, devstack_same_origin, which devstack defines in the root-owned /etc/caddy/Caddyfile. It answers a bare 403 to any request the browser marks as coming from another site: an Origin header that isn't the site's own, or Sec-Fetch-Site: cross-site or same-site. same-site counts too, because sibling names under the dev TLD are one "site" to a browser but may be different projects. Typed URLs, bookmarks and tools (curl, Node, agents) send neither header and pass. No CORS headers are sent in any mode.

caddy.same_originRefused
strict (default)everything from another site, links in included
allow-navigationthe same, except a top-level GET navigation (a link click, an OAuth or payment redirect back); frames and form posts are still refused
offnothing; a risk you confirm with yes

The setting is a project requirement (it goes into infra/devstack-requires.toml), and changing it takes a plain up. A dev server listed in caddy.dev_servers gets its own name with /api/* going to the app, so its page and the API share an origin and need no exception (see The dev browser). caddy.max_request_body (e.g. "4GiB") adds a request_body limit to the generated site block.

What devstack checks

  • Trust roots are pinned in code: the Caddy and PostgreSQL apt key fingerprints, and the Node release keyring (a fixed commit plus its sha256). A swapped download aborts the phase.
  • The phases verify the isolation itself: as each service user, which addresses are reachable; that Caddy's admin port is closed; what sudo allows; who can read and write the app data; and from the container, that your host's services are unreachable.
  • Undo only touches paths the current config would produce, or folders devstack may manage (/etc/dnsmasq.d, /usr/local/share/ca-certificates, the project, ~/.ssh). A journal entry pointing elsewhere is skipped with a warning and kept.
  • db restore runs as the app role over 127.0.0.1, in one transaction. A dump that needs superuser (extensions, COPY ... PROGRAM) fails and changes nothing; the error shows how to restore it manually if you trust the dump. data restore unpacks as the app user, not root.
  • Log files are created with mode 0600, and the app refuses all requests in production if its internal token is missing.

Troubleshooting

name already exists
Preflight found a container, file, volume or ssh alias that this stack didn't create. Pick another stack.name, or remove the old thing yourself if it's really leftover.
dev host doesn't resolve
The host isn't resolving through dnsmasq (check /etc/resolv.conf and your VPN DNS). The proxy phase rolls back. Fix the resolver, then run up again.
browser warns about the certificate
Open the site with ./devstack browse, which trusts the CA from its own profile (it needs certutil: sudo apt install libnss3-tools). Your everyday browser is meant to warn (tls.browser_trust = "no"); if you imported the CA there by hand earlier, remove it at chrome://certificate-manager/localcerts/usercerts. The CA lives on the host, so rebuilding the container keeps it. A new CA is only made if the dev domain changes, and the dev browser picks it up on its next start.
the dev browser can't reach something
That is the point: it reaches only the dev domain. A dev server needs an entry in caddy.dev_servers (a forwarded port lands on your host's loopback, which it can't reach). For anything else, use your everyday browser.
uid mismatch on /srv/<name>
Keep container.uid = "auto". The idmapped mount only lines up when the uid inside matches yours.
volume exists, not owned
The state folder was lost. Set postgres.adopt_volume = true to use the data. devstack then never deletes that volume.
failed phase left for debugging
./devstack status, read the log, then ./devstack up to retry or ./devstack undo to clean up.
another run holds the lock
Only one devstack run per stack at a time. Wait for the other run or end it.

Design choices

  • The project is mounted at /srv/<name>, not under /home. Debian 12+ home folders are private, so Caddy and the hardened service couldn't read them there. It also lets the unit use ProtectHome=yes, which would otherwise have to be turned off.
  • The server binds to 127.0.0.1 from the start, so it's never reachable at http://<container-ip>:8080. The app phase checks it from inside the container, and the browser reaches it through Caddy from proxy on.
  • The container's ssh host key is read through incus exec and pinned, so there's no fingerprint to compare by hand on first connect.
  • Postgres's repo is added the documented manual way. Its data sits on a separate volume with a fixed postgres uid.
  • The default image is debian/13, the current stable release, whatever the host runs. Containers share the host kernel either way. GPU passthrough is available behind gpu.enabled; only GPU services can use it unless gpu.login_user = true (see The GPU).
